# Проектирование и реализация микрофронтендов

## Уровень 1: Проектирование

### Выбор фреймворка
Для создания микрофронтендов я выбрал **Module Federation** — плагин Webpack, позволяющий совместно использовать модули (включая React-компоненты) между различными проектами.  
Этот подход обеспечивает:

- **Изоляцию**: Каждый микрофронтенд является независимым приложением, что позволяет разрабатывать и обновлять их отдельно друг от друга.
- **Динамическое связывание**: Компоненты и модули подгружаются только тогда, когда это необходимо, что снижает общий размер бандлов.
- **Удобное объединение**: Host-приложение (контейнер) управляет маршрутизацией и объединяет все микрофронтенды.

### Архитектура микрофронтендов
Проект состоит из следующих микрофронтендов:

1. **Auth**
    - Отвечает за авторизацию и регистрацию пользователей.
    - Логика: `login`, `register`
    - UI: формы регистрации и входа.

2. **Cards**
    - Управляет карточками (например, добавление, удаление, лайки).
    - Логика: работа с API карточек.
    - UI: отображение списка карточек.

3. **Profile**
    - Управляет профилем пользователя (информация и аватар).
    - Логика: запросы на изменение данных пользователя.
    - UI: форма редактирования профиля.

4. **Host**
    - Контейнерное приложение, которое объединяет микрофронтенды.
    - Управляет маршрутизацией между микрофронтендами.

Каждый микрофронтенд будет иметь следующую структуру:

│   │   │   ├── components/       # UI-компоненты (например, Card, CardList)
│   │   │   ├── utils/            # Логика работы с API (api.js)

│   │   └── package.json

│   │   │   ├── components/       # UI-компоненты (например, ProfileForm, AvatarUploader)

### Уровень 3: Запуск Готового Кода

#### Операции для Запуска
Для запуска готового кода необходимо выполнить следующие шаги:

1. **Переход в директорию**  
   Сначала перейдите в директорию `frontend/microfrontend/host` с помощью команды:
    ```bash
    cd ./frontend/microfrontend/host
    ```
2. **Запуск всех микрофронтендов**  
   Запустите скрип `frontend/microfrontend/host` с помощью команды:
    ```bash
    npm run start:all
    ```

#### Удобный Запуск
Для более удобного и быстрого запуска вы можете использовать цепочку команд, объединив переход в директорию и запуск скрипта в одну строку:
```bash
cd ./repos/architecture-sprint-1/frontend/microfrontend/host && npm run start:all
```
Эта команда сэкономит время, выполнив оба действия последовательно без необходимости вводить каждую команду отдельно.

# Микросервисная система для торговой платформы


## Основные принципы архитектуры

Я решил разделить монолитное приложение на микросервисы, где каждый сервис отвечает за свою конкретную область работы в системе. Сервисы будут взаимодействовать друг с другом через "шину данных", реализованную с помощью Apache Kafka. Это позволит обеспечить высокую производительность, масштабируемость и надежность системы.

## Микросервисы Разбиение

### 1. Auth Service

*   **Описание:** Отвечает за аутентификацию и авторизацию пользователей.
*   **Основные функции:**
   *   Регистрация пользователя
   *   Аутентификация
   *   Присвоение ролей
   *   Валидация токена безопасности
*   **База данных:**
   *   `User`
   *   `Role`
   *   `UserRole`
   *   `SecurityToken`

### 2. Profile Service

*   **Описание:** Хранит информацию о профилях пользователей и управляет их товарами и услугами.
*   **Основные функции:**
   *   Добавление, удаление и изменение товаров и услуг пользователя
*   **База данных:**
   *   `Profile`
   *   `Product`
   *   `Service`

### 3. Order Service

*   **Описание:** Управляет заказами пользователей.
*   **Основные функции:**
   *   Создание, редактирование, сохранение, подтверждение и размещение заказов
   *   Отображение всех заказов и деталей заказа
   *   Определение способа оплаты
*   **База данных:**
   *   `Order`
   *   `OrderItem`
   *   `OrderStatus`

### 4. Auction Service

*   **Описание:** Предоставляет функционал для создания и управления аукционами.
*   **Основные функции:**
   *   Создание, редактирование и обработка новых заявок на аукцион
   *   Обновление ставок и статуса аукциона
*   **База данных:**
   *   `Auction`
   *   `AuctionBid`
   *   `AuctionParticipant`

### 5. Search Service

*   **Описание:** Обеспечивает поиск товаров и услуг, фильтрацию и сортировку результатов.
*   **Основные функции:**
   *   Поиск товаров и услуг
   *   Фильтрация и сортировка результатов
*   **База данных:**
   *   `SearchIndex`
   *   `SearchLog`

### 6. Payment Service

*   **Описание:** Отвечает за обработку платежных операций.
*   **Основные функции:**
   *   Инициирование, учет, авторизация и отмена платежных операций
   *   Предоставление списка и статуса операций
*   **База данных:**
   *   `Transaction`
   *   `PaymentStatus`
   *   `PaymentMethod`

### 7. Support Service

*   **Описание:** Обрабатывает заявки на апелляцию и техническую поддержку.
*   **Основные функции:**
   *   Создание, регистрация и обновление статуса заявок
*   **База данных:**
   *   `Appeal`
   *   `SupportTicket`
   *   `TicketHistory`

### 8. Notification Service

*   **Описание:** Отправляет уведомления пользователям.
*   **Основные функции:**
   *   Нотификация нового пользователя
   *   Нотификация об изменении состояния заказа
   *   Нотификация участника аукциона
*   **База данных:**
   *   `Notification`
   *   `NotificationTemplate`
   *   `NotificationPreference`

### 9. Analytics Service

*   **Описание:** Генерирует отчеты и статистику.
*   **Основные функции:**
   *   Генерация отчетов по продажам
   *   Отображение статистики заказов
   *   Генерация отчетов активности пользователей
*   **База данных:**
   *   `UserActivity`
   *   `SalesReport`
   *   `OrderStatistics`

*   **Описание:** При оформлении заказа Order Service отправляет запрос в Payment Service на инициализацию платежа, передавая идентификатор пользователя, идентификатор заказа и сумму к оплате. Payment Service проверяет корректность данных и подготавливает платёжную операцию.

## Микросервисы Взаимодействие внутренний движок

---

### 1. Инициировать платёж

*   **Producer:** Order Service
*   **Consumer:** Payment Service
*   **Данные:**

```json
{
   "eventType": "PAYMENT_INIT",
   "data": {
      "userId": "user123",
      "orderId": "order456",
      "amount": 1000.00,
      "currency": "USD"
   }
}
```
*   **Описание:** При оформлении заказа Order Service отправляет запрос в Payment Service на инициализацию платежа, передавая идентификатор пользователя, идентификатор заказа и сумму к оплате. Payment Service проверяет корректность данных и подготавливает платёжную операцию.

### 2. Предоставить статус платежа

*   **Producer:** Payment Service
*   **Consumer:** Order Service, Notification Service
*   **Данные:**

```json
{
   "eventType": "PAYMENT_STATUS_CHANGED",
   "data": {
      "transactionId": "tr789",
      "status": "PENDING",
      "orderId": "order456",
      "userId": "user123"
   }
}
```

*   **Описание:** Payment Service после обработки запроса на оплату генерирует ID транзакции, устанавливает статус и отправляет эти данные в Order Service. Notification Service получает событие об изменении статуса для уведомления пользователя.

### 3. Подтверждение платежа

*   **Producer:** Order Service
*   **Consumer:** Payment Service
*   **Данные:**

```json
{
   "eventType": "PAYMENT_STATUS_CHANGED",
   "data": {
      "transactionId": "tr789",
      "orderId": "order456"
   }
}
```
*   **Описание:** Order Service отправляет подтверждение в Payment Service для завершения платёжной операции, передавая идентификатор транзакции.

### 4. Запросить статус платежа

*   **Producer:** Order Service
*   **Consumer:** Payment Service
*   **Данные:**

```json
{
   "eventType": "PAYMENT_STATUS_REQUEST",
   "data": {
      "transactionId": "tr789"
   }
}
```
*   **Описание:** Order Service запрашивает у Payment Service текущий статус транзакции по её идентификатору для обновления статуса заказа.

### 5. Подтверждение отмены платежа

*   **Producer:** Payment Service
*   **Consumer:** Order Service, Notification Service
*   **Данные:**

```json
{
   "eventType": "PAYMENT_STATUS_REQUEST",
   "data": {
      "transactionId": "tr789",
      "status": "CANCELLED",
      "orderId": "order456",
      "userId": "user123",
      "reason": "USER_REQUEST"
   }
}
```
*   **Описание:** Payment Service отправляет уведомление об успешной отмене платежа в Order Service для обновления статуса заказа. Notification Service получает событие об отмене для уведомления пользователя.

## Микросервисы Взаимодействие Интеграционный Движок

---

Данный документ описывает взаимодействие между торговой площадкой и платёжным сервисом через интеграционный движок.

### 1. Запрос на инициацию платежа

**Описание:** Торговая площадка инициирует процесс оплаты, отправляя запрос в платёжный сервис.

**Источник:** Торговая площадка

**Приёмник:** Платёжный сервис

**Данные:**

*   Идентификатор пользователя
*   Идентификатор заказа
*   Сумма заказа

### 2. Ответ о статусе инициации платежа

**Описание:** Платёжный сервис обрабатывает запрос на инициацию, проверяет возможность проведения транзакции и назначает уникальный идентификатор транзакции. Ответ содержит статус инициации и идентификатор транзакции.

**Источник:** Платёжный сервис

**Приёмник:** Торговая площадка

**Данные:**

*   Статус инициации платежа
*   Идентификатор транзакции

### 3. Запрос на подтверждение платежа

**Описание:** Торговая площадка отправляет запрос на подтверждение платежа, используя полученный ранее идентификатор транзакции.

**Источник:** Торговая площадка

**Приёмник:** Платёжный сервис

**Данные:**

*   Идентификатор транзакции

### 4. Запрос статуса платежа

**Описание:** Торговая площадка запрашивает актуальный статус обработки транзакции.

**Источник:** Торговая площадка

**Приёмник:** Платёжный сервис

**Данные:**

*   Идентификатор транзакции

### 5. Уведомление об отмене платежа (альтернативный сценарий)

**Описание:** В случае отмены платежа, платёжный сервис уведомляет торговую площадку об успешной отмене.

**Источник:** Платёжный сервис

**Приёмник:** Торговая площадка

**Данные:**

*   Статус отменённой транзакции
*   Идентификатор транзакции
